  <h1>JSON Web Token (JWT)</h1>

  <p>
    JWT는 웹 표준(RFC 7519)으로, JSON 객체를 사용하여 두 개체 간에 정보를 안전하게 전송하는
    가볍고 자가 수용적인(compact and self-contained) 방식이다.
    이 토큰은 모든 필수 정보를 자체적으로 담고 있어 서버에서 데이터베이스 조회 없이
    토큰만으로 사용자 인증 및 권한 확인이 가능하다.
  </p>

  <p>
    또한 무상태(stateless) 구조로 서버 측 세션의 저장 및 동기화 부담을 줄이고,
    HTTP 헤더나 URL 파라미터로 손쉽게 전달되어 분산 환경에서 확장과 전달이 용이하다는 점으로 인해
    JWT는 현대 웹/마이크로서비스 환경의 핵심 인증 방식으로 자리 잡았다.
  </p>

  <h2>JWT의 구조 및 구성 요소</h2>

  <p>
    JWT는 Header, Payload, Signature 사이에 마침표(.)로 구분되어 있으며
    Base64Url로 인코딩되어 있다.
  </p>

  <h3>Header: 메타 정보</h3>

  <p>
    typ과 alg 클레임을 포함한 토큰의 메타 정보를 담고 있는 부분을 헤더라고 한다.
  </p>

  <pre>
{
  "alg": "HS256", // 서명 알고리즘
  "typ": "JWT"    // 토큰 타입
}
  </pre>

  <h3>Payload: 클레임</h3>

  <p>
    페이로드에는 전송하고자 하는 인증 정보, 권한 정보, 기타 속성 정보가
    JSON 객체 형태로 포함되며 이를 클레임이라고 부른다.
  </p>

  <h4>클레임의 종류</h4>

  <p>
    클레임은 역할에 따라 Registered(표준 정의), Public(공개), Private(사설)
    3가지로 나뉜다.
    Registered Claims에는 토큰의 만료 시점(exp), 발급 시점(iat),
    발급자(iss), 수신자(aud) 등 토큰의 유효성 검증에 활용되는
    표준 필드를 포함한다.
  </p>

  <h4>보안 유의점</h4>

  <p>
    헤더와 페이로드는 암호화가 아닌 단순 인코딩이므로,
    페이로드를 확보하면 손쉽게 디코딩하여 내용 파악이 가능하다.
    따라서 페이로드에는 이메일, 결제 정보 등
    민감한 개인 식별 정보(PII)를 포함해서는 안 된다.
  </p>

  <pre>
{
  "sub": "user123",   // 사용자 ID
  "name": "John Doe", // 사용자 이름
  "role": "admin",    // 권한
  "iat": 1516239022,  // 발급 시각
  "exp": 1516242622   // 만료 시각
}
  </pre>

  <h3>Signature: 무결성 보장</h3>

  <p>
    Signature는 토큰의 무결성(Integrity) 및 신뢰성(Authenticity)을 보장하는 핵심 요소다.
    서명은 인코딩된 Header와 Payload, 그리고 서버가 보관하는
    Secret Key(HS256) 또는 Private Key(RS256)를 결합해
    지정된 알고리즘에 따른 암호학적 서명 연산으로 계산된다.
  </p>

  <p>
    서버는 서명을 재계산하여 수신된 서명과 일치하는지 확인하며,
    이를 통해 토큰의 위변조 여부를 판단한다.
    비밀 서명 키를 모르는 공격자는 유효한 서명을 생성할 수 없다.
  </p>

  <h2>세션 기반 인증 방식과 JWT 인증 방식의 비교</h2>

  <p>
    세션 기반 인증 방식은 크게 4가지의 단점을 지닌다.
    하지만 JWT 인증 방식은 세션 기반 인증 방식의 단점을
    어느 정도 해소한다.
  </p>

  <h3>세션 기반 인증 방식의 4가지 단점</h3>

  <ul>
    <li>서버가 세션 상태를 직접 관리해야 하는 Stateful 구조</li>
    <li>서버 수평 확장 시 세션 공유(공동 세션 스토어, Sticky Session 등)가 필요</li>
    <li>세션 저장소(DB, Redis 등)에 대한 추가 부하 및 운영 비용 발생</li>
    <li>중앙 세션 저장소에 의존하기 때문에 마이크로서비스 및 분산 아키텍처에서 유연성이 떨어질 수 있음</li>
  </ul>

  <h3>JWT 인증 방식이 단점을 해소하는 이유</h3>

  <ul>
    <li>Stateless 구조로 별도의 세션 저장소 없이 서명 검증만으로 기본 인증 가능</li>
    <li>서버/인스턴스 간 세션 동기화가 필요 없어 수평 확장에 유리</li>
    <li>각 서비스가 토큰을 직접 검증할 수 있어 마이크로서비스 아키텍처에 친화적</li>
    <li>토큰에 사용자 식별자, 권한, 만료 시간 등을 포함하여 서버 상태 의존도를 줄임</li>
  </ul>

  <h2>JWT 보안 취약점</h2>

  <p>
    JWT의 취약점은 주로 서명 검증 로직의 구현 오류나,
    사용자가 조작 가능한 Header 파라미터를
    서버가 무분별하게 신뢰할 때 발생한다.
  </p>

  <p>
    JWT의 핵심 장점인 Stateless 특성은 운영 설계가 미흡할 경우
    치명적인 약점으로 작용할 수 있다.
  </p>

  <p>
    전통적으로 세션 방식은 서버에서 세션을 삭제할 경우
    강제 로그아웃이 즉시 반영되지만,
    JWT는 클라이언트가 보관하므로 서버가 토큰을 즉시 회수하기 어렵고
    별도의 철회 메커니즘이 없다면 만료 시점까지 유효할 수 있다.
  </p>

  <p>
    서명 키가 유출되면 공격자는 임의의 사용자로 가장하거나
    권한을 상승시킨 토큰을 생성할 수 있으며,
    실제로 인증 토큰 위조를 통한 대규모 데이터 유출 사례가 보고된 바 있다.
  </p>

  <h2>결론</h2>

  <p>
    JWT 기반 인증 시스템의 보안 실패는 곧 기업의 핵심 자산에 대한
    광범위한 침해로 이어질 수 있다.
    따라서 서명 키를 HSM 또는 KMS 내부에 격리하고,
    비대칭 키 기반(RS256) 전환과 키 회전 정책을
    최우선 과제로 설정해야 한다.
  </p>
