  <h2>JSON Web Token (JWT)</h2>

  <p>
    JWT는 웹 표준(RFC 7519)으로, JSON 객체를 사용하여 두 개체 간에 정보를 안전하게 전송하는
    가볍고 자가-수용적인(compact and self-contained) 인증 토큰 방식이다.
    토큰 자체에 모든 인증 정보를 포함하므로 서버 측 세션 저장소가 필요 없는
    Stateless 인증 구조를 구현할 수 있다.
  </p>

  <p>
    이 특성 덕분에 JWT는 마이크로서비스, 분산 시스템, API 기반 아키텍처에서
    확장성과 전달성이 뛰어난 인증 방식으로 널리 사용된다.
  </p>

  <h2>JWT의 구조</h2>

  <p>
    JWT는 다음 세 부분으로 구성되며, 각 요소는 마침표(.)로 구분되고
    Base64Url 방식으로 인코딩된다.
  </p>

  <ul>
    <li>Header</li>
    <li>Payload</li>
    <li>Signature</li>
  </ul>

  <h3>Header – 메타 정보</h3>

  <p>
    Header에는 토큰의 타입과 서명 알고리즘 정보가 포함된다.
  </p>

  <pre><code>{
  "alg": "HS256",
  "typ": "JWT"
}</code></pre>

  <h3>Payload – Claims</h3>

  <p>
    Payload에는 사용자 식별자, 권한 정보, 토큰 유효성 검증에 필요한
    클레임(Claims)이 포함된다.
    이 데이터는 암호화되지 않으며 단순 인코딩만 수행된다.
  </p>

  <p><strong>클레임의 종류</strong></p>

  <ul>
    <li><strong>Registered Claims</strong>: exp, iat, iss, aud 등 표준 정의</li>
    <li><strong>Public Claims</strong>: 충돌 방지를 위해 URI 형태로 정의</li>
    <li><strong>Private Claims</strong>: 서비스 내부 용도</li>
  </ul>

  <p><strong>보안 유의사항</strong></p>

  <p>
    Payload는 누구나 디코딩할 수 있으므로 이메일, 결제 정보,
    주민번호와 같은 민감한 개인 식별 정보(PII)를 포함해서는 안 된다.
  </p>

  <pre><code>{
  "sub": "user123",
  "name": "John Doe",
  "role": "admin",
  "iat": 1516239022,
  "exp": 1516242622
}</code></pre>

  <h3>Signature – 무결성 보장</h3>

  <p>
    Signature는 토큰의 무결성과 신뢰성을 보장하는 핵심 요소다.
    인코딩된 Header와 Payload, 그리고 서버가 보관하는 비밀 키(HS256)
    또는 개인 키(RS256)를 기반으로 암호학적 서명을 생성한다.
  </p>

  <p>
    서버는 서명을 재계산하여 토큰 위변조 여부를 검증하며,
    키를 알지 못하는 공격자는 유효한 토큰을 생성할 수 없다.
  </p>

  <h2>세션 기반 인증과 JWT 인증 비교</h2>

  <h3>세션 기반 인증의 한계</h3>

  <ul>
    <li>Stateful 구조로 서버가 세션을 직접 관리</li>
    <li>수평 확장 시 세션 공유 필요</li>
    <li>세션 저장소 부하 및 운영 비용 증가</li>
    <li>마이크로서비스 환경에 부적합</li>
  </ul>

  <h3>JWT 인증의 장점</h3>

  <ul>
    <li>Stateless 구조로 확장성 우수</li>
    <li>중앙 세션 저장소 불필요</li>
    <li>서비스 간 독립적인 토큰 검증 가능</li>
    <li>분산 아키텍처에 적합</li>
  </ul>

  <h2>JWT 보안 취약점</h2>

  <p>
    JWT의 주요 취약점은 서명 키 관리 실패,
    알고리즘 검증 미흡,
    토큰 철회 메커니즘 부재에서 발생한다.
  </p>

  <p>
    토큰이 클라이언트에 저장되기 때문에 서버에서 즉각적인 무효화가 어렵고,
    서명 키 유출 시 인증 체계 전체가 붕괴될 수 있다.
  </p>

  <h2>탐지 및 방어 전략</h2>

  <h3>1. 안전한 키 관리</h3>

  <ul>
    <li>HSM 또는 클라우드 KMS 사용</li>
    <li>애플리케이션 서버에서 키 직접 접근 금지</li>
    <li>비대칭 키(RS256) 사용 권장</li>
    <li>정기적인 키 회전(Key Rotation)</li>
  </ul>

  <h3>2. 엄격한 토큰 검증</h3>

  <ul>
    <li>알고리즘 화이트리스트 고정</li>
    <li>exp, iss, aud 클레임 필수 검증</li>
    <li>kid, jku, jwk 입력값 검증 및 제한</li>
  </ul>

  <h3>3. 토큰 수명 및 무효화 관리</h3>

  <ul>
    <li>Access Token 짧은 만료 시간 설정</li>
    <li>Refresh Token 분리 및 회전 정책 적용</li>
    <li>Revocation List 기반 실시간 차단</li>
  </ul>

  <h3>4. 침해 탐지 및 모니터링</h3>

  <ul>
    <li>JWT 검증 실패 이벤트 로깅</li>
    <li>SIEM 연동</li>
    <li>Replay Attack 및 이상 패턴 탐지</li>
  </ul>

  <h2>결론</h2>

  <p>
    JWT 기반 인증 시스템의 보안 실패는
    인증 체계 전체를 무력화할 수 있는 치명적인 리스크다.
    키 관리 강화, 비대칭키 전환, 엄격한 검증 로직,
    그리고 실시간 탐지 체계 구축이 필수적이다.
  </p>
